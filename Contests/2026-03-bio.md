## [H-01] ERC20 Transfer `to` recipient is ignored during deposit processing

**Issue:** [#30](https://github.com/PashovAuditGroup/Bio_March26_MERGED/issues/30)

### Summary
In `process_transaction.rs`, when processing an ERC20 `Transfer` log, the decoded `to` field is discarded. An attacker can submit a valid Transfer log for a mapped token sent to an arbitrary address (not the protocol escrow) and still receive unbacked receipt tokens.

### Root Cause
```
// process_transaction.rs:57
let ERC20::Transfer { from, to: _, value } =
    ERC20::Transfer::decode_raw_log(topics, log.data.as_ref())
```

The code then calls `process_deposit()` using only `from` (as the user to credit) and `log.address` (as the token identifier). The transfer destination is never validated against a registered escrow or gateway address. An inline TODO at line 55 confirms the gap:

```
// TODO: register escrow addresses with rollup and verify transfer.to
```

Transaction-level `from` and `to` in `TxVerificationData::Evm` are also discarded.

### Impact
`process_deposit()` mints receipt tokens to the `from` address and increments `spice_escrow_ledger` even though no value arrived in protocol custody. The escrow ledger becomes inflated and the attacker receives unbacked receipt tokens.

### Mitigation
Before calling `process_deposit()`, validate that `log.address` is a registered token for the chain and that decoded `Transfer.to` equals a registered escrow/gateway address. Also cross-check the transaction-level `to` from `TxVerificationData::Evm`.

## [H-02] Attacker can front-run PancakeSwap V3 pool creation at manipulated price

**Issues:** [#27](https://github.com/PashovAuditGroup/Bio_March26_MERGED/issues/27) · [#26](https://github.com/PashovAuditGroup/Bio_March26_MERGED/issues/26) · [#23](https://github.com/PashovAuditGroup/Bio_March26_MERGED/issues/23)

### Summary
When a launch is finalized on BSC, the protocol deploys a new agent token via `Clones.cloneDeterministic()` and creates a PancakeSwap V3 pool through `createAndInitializePoolIfNecessary()`. The future token address is fully predictable, and pool creation is permissionless. An attacker can pre-create the pool at a manipulated price. `launch()` then reuses that pool without verifying `sqrtPriceX96`, and mints the entire initial liquidity with `amount0Min: 0` / `amount1Min: 0`.

### Root Cause
The CREATE2 salt is public:

```
keccak256(abi.encodePacked(msg.sender, launchName()))
```

`PancakeV3Adapter.launch()` never checks the pool’s actual price after `createAndInitializePoolIfNecessary` returns, and the subsequent mint hardcodes zero slippage:

```
amount0Min: 0,
amount1Min: 0,
```

If the pool already exists, PancakeSwap returns it without resetting price.

### Attack Path
1. Attacker monitors the BSC mempool for `Execute.execute()` / `LaunchFactory.onLaunchSuccess()`.
2. Attacker computes the future agent token address from public `launchName()`, factory address, and `tokenImplementation()`.
3. Attacker front-runs `createAndInitializePoolIfNecessary` with a manipulated `initialSqrtPriceX96`.
4. Finalization lands second, clones the token at the predicted address, and deposits all initial LP at the attacker price.
5. Attacker arbitrages the pool back to fair value and extracts value from launch liquidity.

### Impact
The entire initial LP deposit is minted at the wrong price ratio. The attacker extracts a material fraction of LP value. For a launch with e.g. $50K USDC + agent tokens as LP, tens of thousands of dollars can be extracted.

### Mitigation
After `createAndInitializePoolIfNecessary`, read `slot0().sqrtPriceX96` and revert if it does not match the intended price. Also pass non-zero `amount0Min` / `amount1Min` into `mint()`.

## [H-03] Incorrect sqrtPrice calculation for BYOT liquidity setup

**Issue:** [#24](https://github.com/PashovAuditGroup/Bio_March26_MERGED/issues/24)

### Summary
BYOT liquidity setup incorrectly calculates `sqrtPrice` when the base token and BYOT token have different decimals. Amounts are normalized by dividing out decimals, but Uniswap/Pancake V3 prices are based on raw amounts, not unit-normalized amounts.

### Root Cause
`TokenFactory.sol`:

```
uint256 normalizedAmount0 = amount0 / (10 ** decimals0);
uint256 normalizedAmount1 = amount1 / (10 ** decimals1);
uint256 ratioX96 = (normalizedAmount1 << 96) / normalizedAmount0;
uint160 sqrtPrice = uint160(_sqrt(ratioX96) * (1 << 48));
```

If the base token has 6 decimals and the BYOT token has 18 decimals, the sqrt price is off by 6 decimal places.

### Impact
Initial pool price is wrong. Arbitrage bots profit at launch against the protocol’s LP.

### Mitigation
Do not normalize amounts; use raw amounts. Use `mulDiv` to prevent overflow.

## [M-01] Failed withdrawals have no recovery path, permanently locking user value

**Issue:** [#29](https://github.com/PashovAuditGroup/Bio_March26_MERGED/issues/29)

### Summary
When a withdrawal is created in `execute_intent_auth()`, receipt tokens are transferred to admin and the escrow ledger is decremented immediately. The only implemented state transition is `Created -> Successful`. There is no path to mark a request `Failed`, refund the user, or restore escrow.

### Root Cause
`WithdrawalRequestState::Failed` exists as an enum variant, but no in-scope code transitions a request to `Failed`, refunds receipt tokens from admin, or restores the escrow ledger. If the destination-chain withdrawal fails, user value stays locked in admin custody.

### Impact
Permanent lock of user withdrawal value with no recovery mechanism.

### Mitigation
Implement an explicit failure/cancellation flow that sets state to `Failed`, restores escrow via `checked_add`, returns receipt tokens to the user, and removes the request from `withdrawal_request_ids_active`.

## [M-02] LP slippage protection ignored — hardcoded min 0

**Issues:** [#28](https://github.com/PashovAuditGroup/Bio_March26_MERGED/issues/28) · [#21](https://github.com/PashovAuditGroup/Bio_March26_MERGED/issues/21) · [#17](https://github.com/PashovAuditGroup/Bio_March26_MERGED/issues/17)

### Summary
`ILPProvider.MintParams` documents `amountAMin` / `amountBMin` slippage fields. `Execute._mintLP()` forwards them, but `PancakeV3Adapter.mintLP()` (and `launch()`) discards them and hardcodes `amount0Min: 0`, `amount1Min: 0`.

### Root Cause
```
amount0Min: 0,
amount1Min: 0,
```

On BSC, transactions go through a public mempool. An unprivileged attacker can sandwich the admin’s honest `Execute.execute()` call, manipulate the pool price, and extract value from the protocol.

### Impact
Protocol / launch LP loses value to MEV even though the admin operated correctly and supplied slippage limits.

### Mitigation
Forward caller-supplied minimums:

```
amount0Min: params.tokenA == token0 ? params.amountAMin : params.amountBMin,
amount1Min: params.tokenA == token0 ? params.amountBMin : params.amountAMin,
```

## [M-03] Precision loss in sqrtPriceX96 calculation for existing token launches

**Issue:** [#16](https://github.com/PashovAuditGroup/Bio_March26_MERGED/issues/16)

### Summary
In `TokenFactory._setupExistingTokenLiquidity()`, integer division by `10 ** decimals` happens before the Q96 bit-shift, discarding sub-unit precision.

### Root Cause
```
uint256 normalizedAmount0 = amount0 / (10 ** decimals0);
uint256 normalizedAmount1 = amount1 / (10 ** decimals1);
uint256 ratioX96 = (normalizedAmount1 << 96) / normalizedAmount0;
```

1.5 tokens round down to 1 (33% error). Less than 1 whole unit (e.g. 999,999 units of a 6-decimal token) rounds to 0 and fails the requirement.

### Impact
Initial pool price can deviate significantly from the intended ratio, enabling launch-time arbitrage.

### Mitigation
Scale before division, or require amounts to be evenly divisible.

## [M-04] Missing V3 staking — missed CAKE rewards

**Issue:** [#18](https://github.com/PashovAuditGroup/Bio_March26_MERGED/issues/18)

### Summary
Pancake V3 supports extra liquidity-mining rewards via MasterChef V3, but the adapter/locker flow never stakes LP NFTs there. Users miss valid CAKE incentives.

### Root Cause
Swap fees accrue on the LP NFT automatically. CAKE LM rewards are only paid if the NFT is staked in MasterChef V3. The current locker never deposits the NFT.

### Impact
Launch LPs permanently miss CAKE incentives that the pool is otherwise eligible for.

### Mitigation
Add optional MasterChef V3 integration: deposit LP NFT, harvest rewards, unstake on unlock.

## [M-05] Leftover token refund incorrectly sent and stuck

**Issues:** [#15](https://github.com/PashovAuditGroup/Bio_March26_MERGED/issues/15) · [#2](https://github.com/PashovAuditGroup/Bio_March26_MERGED/issues/2)

### Summary
After LP minting, `PancakeV3Adapter.launch()` refunds leftovers to `msg.sender`. In the BYOT flow that is `TokenFactory`, which has no withdrawal path. In the initial launch flow that is the newly deployed Token contract, and `withdrawERC20(address(this))` is blocked, so self-token leftovers are stuck.

### Impact
Creator tokens and user-contributed base tokens leftover from LP math accumulate with no recovery path.

### Mitigation
Pass an explicit refund recipient and route leftovers to the Launch contract, project treasury, or creator, with a withdrawal mechanism.

## [M-06] Existing token vesting reverts during finalization for non-18 decimal tokens

**Issue:** [#14](https://github.com/PashovAuditGroup/Bio_March26_MERGED/issues/14)

### Summary
`LaunchFactory.createExistingTokenLaunch()` accepts tokens with 1–18 decimals, but `AgentVestingToken.initialize()` reverts unless the underlying token has exactly 18 decimals.

### Attack Path
1. A BYOT launch is created with a non-18 decimal token — validation passes.
2. Users participate and send base tokens.
3. Admin calls `execute()` to finalize.
4. `_createNewAgentVestingToken()` → `AgentVestingToken.initialize()` reverts with `DecimalsError()`.
5. The launch cannot be finalized.

### Impact
Users’ base tokens are stuck in a launch that can never complete.

### Mitigation
Require exactly 18 decimals in `createExistingTokenLaunch()`, or support variable decimals in `AgentVestingToken`.

## [L-01] Tick spacing validation in launch does not match PancakeV3Adapter

**Issues:** [#13](https://github.com/PashovAuditGroup/Bio_March26_MERGED/issues/13) · [#10](https://github.com/PashovAuditGroup/Bio_March26_MERGED/issues/10)

### Summary
`Launch._onLaunchSuccess()` allows tick spacings `[1, 50, 100, 200, 2000]` (Aerodrome / Base). `PancakeV3Adapter` maps `[1, 10, 50, 200]`. Spacings 100 and 2000 pass Launch validation then revert with `InvalidFee()` on BSC. Spacing 10 is valid on Pancake but blocked by Launch.

### Mitigation
Make tick-spacing validation chain-aware, or delegate it to the adapter.

## [L-03] `LaunchFactory.onLaunchSuccess` can be called again for a failed launch

**Issues:** [#9](https://github.com/PashovAuditGroup/Bio_March26_MERGED/issues/9) · [#1](https://github.com/PashovAuditGroup/Bio_March26_MERGED/issues/1)

### Summary
When a launch is marked failed, token state is set to false, but `onLaunchSuccess` does not check that state and can be called again. `isFailed` can be set true and is never cleared. A later “success” path can still deploy a token while `isFailed` stays true, blocking claims and marking users as incorrectly refund-eligible.

### Mitigation
Enforce single finalization, or explicitly reset `isFailed` and token state on a successful retry.

## [L-04] Reward claim inconsistency between adapters

**Issue:** [#3](https://github.com/PashovAuditGroup/Bio_March26_MERGED/issues/3)

### Summary
Aerodrome adapter supports reward handling while the position is locked. Pancake adapter locks the NFT in `SimpleLPLocker` with no reward-claim path, so users must wait until unlock.

### Mitigation
Add a claim path for locked Pancake positions, matching Aerodrome behavior.
