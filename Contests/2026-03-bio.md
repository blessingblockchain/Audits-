## [H-01] ERC20 Transfer `to` recipient is ignored during deposit processing which can cause an attacker to mint unbacked tokens

### Severity

**Impact:** High

**Likelihood:** High

### Description

In `process_transaction.rs:57`, when processing an `ERC20` Transfer log, the decoded to field is explicitly discarded `(to: _)`:

```
// process_transaction.rs:57
let ERC20::Transfer { from, to: _, value } =
    ERC20::Transfer::decode_raw_log(topics, log.data.as_ref())
```

The code then calls `process_deposit()` at line 64 using only `from` (as the user to credit) and `log.address` (as the token identifier). 

At no point is the transfer destination validated against a registered escrow or gateway address. The `inline TODO` at line 55 confirms this is a known gap:
```
// process_transaction.rs:55
// TODO: register escrow addresses with rollup and verify transfer.to
```

Additionally, the transaction-level `from` and `to` in `TxVerificationData::Evm (tx_verification_data.rs:20-21)` are also discarded at `process_transaction.rs:37-38:`

```
// process_transaction.rs:37-38
from: _,
to: _,
``` 


This means an attacker who can submit a `ProcessTransaction` call message containing a `valid ERC20` Transfer log for a mapped token, ` where the transfer was sent to any arbitrary address, not the protocol escrow which  would cause `process_deposit() (process_transaction.rs:127-163)` to mint receipt tokens to the `from address` and increment `spice_escrow_ledger` at line 140, despite no value actually arriving in the protocol's custody. The escrow ledger becomes inflated, and the attacker receives unbacked receipt tokens.

### Recommendations
Before calling `process_deposit()`, validate both:

- `log.address` is a registered token contract for the given `chain_hash.chain_id`.
- The decoded `Transfer.to` equals a registered escrow/gateway address for that token and chain.

Also incorporate the transaction-level `to` from `TxVerificationData::Evm` as an additional cross-check,  verifying the transaction itself was directed at the escrow contract.

## [H-02] Attacker can front-run PancakeSwap V3 pool creation at manipulated price

### Severity

**Impact:** Medium

**Likelihood:** High


### Description

When a launch is finalized on BSC, the protocol deploys a new agent token via `Clones.cloneDeterministic()` and immediately creates a `PancakeSwap V3` pool for it by calling `createAndInitializePoolIfNecessary()`. The protocol intends for the pool to be initialized at a specific `initialSqrtPriceX96` computed from the launch's reserve and token supply ratios.

[check here](https://docs.uniswap.org/contracts/v3/reference/periphery/base/PoolInitializer) However, the future agent token address is fully predictable before the finalization transaction lands, and `PancakeSwap V3's` pool creation is permissionless and does not require the `token contract` to exist. An attacker can front-run the finalization transaction by pre-creating and initializing the pool at an attacker-chosen price. The protocol's `launch()` function then reuses this attacker-initialized pool without verifying its price, depositing the entire initial liquidity at the wrong price. The attacker subsequently arbitrages the mispriced pool to extract value from the deposited liquidity.

### Why the token address is predictable:

The salt used for `Clones.cloneDeterministic()` is computed at `Launch.sol` line 471:

```
keccak256(abi.encodePacked(msg.sender, launchName()))
```

Both inputs are public:

- `msg.sender` in `Launch.onLaunchSuccess()` is the `LaunchFactory` address, which contributes to the public salt. The token itself is then deployed deterministically by `AgentFactory`, which is the actual CREATE2 deployer.
- `launchName()` is a public view function on the `Launch` contract.

The token implementation address is also public via `AgentFactory.tokenImplementation()` (line 234).

The protocol even exposes a helper to compute the exact future address:

```
function getPredeterministicAddress(address implAddress, bytes32 salt) public view returns (address) {
    return Clones.predictDeterministicAddress(implAddress, salt);
}
```

So an attacker can call `getPredeterministicAddress(tokenImplementation(), keccak256(abi.encodePacked(launchFactory, launchName)))` and get the exact address of the not yet deployed agent token.

### Why PancakeSwap allows this:

PancakeSwap V3's `PancakeV3Factory.createPool()` does not check whether token addresses have deployed contract code. It only validates:

- `tokenA != tokenB`
- `token0 != address(0)`
- Fee tier is enabled
- Pool does not already exist

[check here](https://github.com/pancakeswap/pancake-v3-contracts/blob/main/projects/v3-periphery/contracts/base/PoolInitializer.sol)

`PoolInitializer.createAndInitializePoolIfNecessary()` (inherited by the `NonfungiblePositionManager`) performs no token code check. It creates the pool, calls `pool.initialize(sqrtPriceX96)`, and returns.

### Why the protocol does not defend against this:

`PancakeV3Adapter.launch()` at lines 144-145:

```
address pool = pancakeNfpm.createAndInitializePoolIfNecessary(
    token0, token1, fee, params.initialSqrtPriceX96
);
```

If the pool already exists and is already initialized, `createAndInitializePoolIfNecessary` simply returns the existing pool address without modifying its price. The adapter never reads the pool's actual `sqrtPriceX96` after this call and never compares it against `params.initialSqrtPriceX96`. It proceeds directly to minting liquidity with `amount0Min: 0` and `amount1Min: 0` (lines 164-165).

### Attack flow:

1 - The attacker monitors the BSC public mempool for the `Execute.execute()` or `LaunchFactory.onLaunchSuccess()` finalization transaction.

2 - The attacker reads the public state to compute the future agent token address:

- calls `Launch.launchName()` on the target launch contract
- reads `LaunchFactory` proxy address on-chain
- computes `salt = keccak256(abi.encodePacked(launchFactoryAddress, launchName))`
- calls `AgentFactory.tokenImplementation()` to get the implementation address
- The attacker can compute the exact future token address using the public token implementation, the public salt, and `AgentFactory` as the CREATE2 deployer.

3 - Attacker submits a higher-gas transaction calling `PancakeSwap V3's` public `NonfungiblePositionManager.createAndInitializePoolIfNecessary(predictedTokenAddress, pairToken, fee, manipulatedSqrtPriceX96)`. This creates and initializes the pool at the attacker’s chosen price.

4 - The attacker’s transaction lands first due to higher gas. The pool now exists at the manipulated price.

5 - The finalization transaction lands second. Inside the call chain:

- `Launch._onLaunchSuccess()` calls `AgentFactory.executeFactoryApplicationSalt()`
- `AgentFactory._executeApplication()` clones the agent token at the predicted address
- `AgentToken.addInitialLiquidity()` calls `lpProvider.launch()`
- `PancakeV3Adapter.launch()` calls `createAndInitializePoolIfNecessary()`, i.e., the pool already exists, and the price is not reset
- `pancakeNfpm.mint()` deposits all initial liquidity at the attacker's manipulated price with zero slippage protection

6 - Attacker swaps against the mispriced pool, moving the price toward fair value. The difference between the manipulated price and the fair price is extracted as profit directly from the launch's deposited liquidity.

### Impact:

- The entire initial LP deposit (agent tokens + base tokens) is minted at a fundamentally wrong price ratio.
- The protocol may mint its initial LP position against an attacker-controlled initial price, causing a materially imbalanced deployment of launch liquidity. The attacker can then arbitrage the pool toward fair value and extract value from the portion of liquidity actually deployed.
- The attacker extracts a material fraction of the LP value through arbitrage.
- The protocol's LP position suffers permanent impermanent loss equivalent to the full price manipulation range. For a launch with $50K USDC + 1M agent tokens as LP, the attacker can extract tens of thousands of dollars.

### Recommendations

Verify pool price after creation. After `createAndInitializePoolIfNecessary` returns, read the pool's actual `slot0().sqrtPriceX96` and revert if it does not match `params.initialSqrtPriceX96` within an acceptable tolerance:

```
address pool = pancakeNfpm.createAndInitializePoolIfNecessary(token0, token1, fee, params.initialSqrtPriceX96);

(uint160 actualPrice,,,,,, ) = IPancakeV3Pool(pool).slot0();
require(
    actualPrice == params.initialSqrtPriceX96,
    "Pool price does not match intended initial price"
);
```

Alternatively, enforce non-zero minimum amounts in the `launch()` call to `pancakeNfpm.mint` (pass computed `amount0Min` and `amount1Min` rather than 0), so that even if the pool is pre-initialized at a manipulated price, the mint reverts rather than accepting an imbalanced deposit.

## [H-03] Attacker can frontrun post launch action to compromise initial price

### Severity

**Impact:** High

**Likelihood:** Medium

### Description

Token launch process adds initial liquidity to pancake v3 pool. The expected `sqrtPrice` is calculated from `tokenLpSupply` and `reserveForLP`. And it is assumed that intial price will be determined by these pre-configured parameters.

However, since new token address is deterministic, an attacker can frontrun `Execute.execute` transaction and  intialize the pool for `(token, baseToken)` pair with their wanted price.

Consider the following scenario:

- A token launch is successful and `Execute.execute` -> `Launch._onLaunchSuccess` tx is submitted on mempool
- An attacker fronruns the tx with direct call to `pancakeNfpm.createAndInitializePoolIfNecessary` with the following parameters:
    - `token0`: base token (considering if `baseToken < newToken`)
    - `token1`: deterministic address calculated from token implementation address and `salt = keccak256(abi.encodePacked(address(LaunchFactory), launchName)`
    - `fee`: Same fee defined in `PancakeV3Adapter`
    - `initialSqrtPriceX96`: attacker provided price

After attacker's fronrun tx, `Execute.execute` will be executed and the following will happen:

- In `PancakeV3Adapter.launch`, `pancakeNfpm.createAndInitializePoolIfNecessary` will reuse attacker-created pool, since it shares same `(token0, token1, fee)` parameters
- Initial liquidity minting will not revert because `amount0Min` and `amount1Min` are overrided with 0

Thus, initial liquidity is provided with attacker-controlled ratio. The attacker can backrun with an arbitrage swap to take profit.

### Recommendations

Verify initialized pool's `sqrtPrice` matches target `sqrtPrice`

## [H-05] Zero Slippage Protection in PancakeV3Adapter LP Minting

### Severity

**Impact:** High

**Likelihood:** Medium

### Description

The LP minting parameters in `PancakeV3Adapter.launch()` explicitly set zero slippage protection:

```solidity
(lpTokenId, liquidity,,) = pancakeNfpm.mint(
    IPancakeNfpm.MintParams({
        token0: token0,
        token1: token1,
        fee: fee,
        tickLower: tickLower,
        tickUpper: tickUpper,
        amount0Desired: amount0,
        amount1Desired: amount1,
        amount0Min: 0,
        amount1Min: 0,
        recipient: mintRecipient,
        deadline: block.timestamp
    })
);
```

The `launch()` function uses `createAndInitializePoolIfNecessary()` to create the pool. If the pool already exists (e.g., created by an attacker front-running the transaction), the function returns the existing pool without modifying its price. The subsequent `mint()` call then provides liquidity at whatever price the pool currently has, with zero minimum output enforced.

This exposes every launch to price manipulation:
1. Attacker sees launch transaction in the mempool
2. Attacker front-runs by creating a pool (with same token0, token1, fee) with a skewed price
3. `createAndInitializePoolIfNecessary` returns the attacker's pool
4. LP is minted at the skewed price with `amount0Min: 0, amount1Min: 0`
5. Attacker back-runs to restore price, extracting value

On BSC where PancakeV3 operates, MEV extraction is active and profitable. Launch creators and participants bear the cost through a worse token ratio in the LP position.

### Recommendations

Consider adding parameters for minimum amounts.

## [M-02] Lp slippage protection ignored in PancakeV3Adapter.mintLP with hardcoded min 0

### Severity

**Impact:** Medium

**Likelihood:** Medium


### Description

`ILPProvider.MintParams` explicitly documents slippage protection fields:

        uint256 amountAMin;
        /// @notice Minimum amount of tokenB (slippage protection)
        uint256 amountBMin;
```

`Execute._mintLP()` faithfully forwards these values from the admin's calldata into the struct passed to the LP provider. However, `pancakeV3adapter.sol` discards them.

- `PancakeV3Adapter.mintLP()` at lines 229-230:

```

                amount1Min: 0,
```

On BSC (PancakeSwap), transactions go through a public mempool. An external attacker can sandwich the admin's `Execute.execute()` transaction, manipulating the pool price before the LP mint and extracting value from the protocol. Forward the caller-supplied minimums to the underlying NFPM calls:

```

amount1Min: params.tokenA == token0 ? params.amountBMin : params.amountAMin,

## [M-06] Precision loss in sqrtPriceX96 calculation for existing token launches

### Severity

**Impact:** Low

**Likelihood:** High


### Description

In `TokenFactory._setupExistingTokenLiquidity()`, the price calculation performs integer division before the Q96 bit-shift:

```solidity
uint256 normalizedAmount0 = amount0 / (10 ** decimals0);
uint256 normalizedAmount1 = amount1 / (10 ** decimals1);

require(normalizedAmount0 > 0 && normalizedAmount1 > 0, "Amounts too small after normalization");

uint256 ratioX96 = (normalizedAmount1 << 96) / normalizedAmount0;
uint160 sqrtPrice = uint160(_sqrt(ratioX96) * (1 << 48));
```

Dividing by `10 ** decimals` before the Q96 bit-shift discards all sub-unit precision. For example, 1.5 tokens round down to 1, a 33% error. Less than 1 whole unit of tokens (e.g., 999,999 units of a 6-decimal token = 0.999999) round down to 0, failing the requirement. The initial pool price may significantly deviate from the intended ratio, allowing arbitrage bots to profit at launch.

### Recommendations

Preserve precision by scaling before division or require the amounts to be evenly divisible (using the modulo operator).

## [M-07] Leftover token refund incorrectly sent to TokenFactory

### Severity

**Impact:** Low

**Likelihood:** High


### Description

After LP minting in `PancakeV3Adapter.launch()`, leftover tokens are refunded to `msg.sender`:

```solidity
// Refund unused tokens (order doesn't matter — both get refunded)
_refundLeftover(params.launchToken, msg.sender);
_refundLeftover(params.pairToken, msg.sender);
```

In the BYOT flow:

1. Launch contract transfers tokens to TokenFactory
2. TokenFactory calls `_setupExistingTokenLiquidity()` which calls `lpProvider.launch()`
3. PancakeV3Adapter refunds leftovers to `msg.sender` (TokenFactory)
4. TokenFactory has no mechanism to return these to the users or the token creator.

Leftover tokens from LP minting accumulate in TokenFactory with no withdrawal mechanism. `launchToken` represents the creator's existing tokens and `pairToken` represents the base tokens contributed by the users. The amounts depend on LP math but can be non-trivial.

The same issue affects the initial (non-BYOT) token launch flow: `msg.sender` in `PancakeV3Adapter.launch()` is the newly deployed Token contract, and any self-token refund accumulates in that contract with no recovery path because `withdrawERC20(address(this))` is blocked on the Token contract.

### Recommendations

Consider passing a refund recipient to the adapter and routing leftovers to the Launch contract, the project treasury, or the creator. Note that the Merkle-based claim system cannot redistribute post-LP-mint residuals to users, so sending leftovers back to the Launch contract alone is not sufficient without an additional withdrawal mechanism.

## [L-01] Tick spacing validation in launch does not match PancakeV3Adapter

### Description

`Launch._onLaunchSuccess()` hardcodes the allowed tick spacings:

```solidity
require(
    tickSpacing == 1 || tickSpacing == 50 || tickSpacing == 100 || tickSpacing == 200 || tickSpacing == 2000,
    "Invalid tickSpacing"
);
```

These values correspond to Aerodrome (Base chain) tick spacings. However, `PancakeV3Adapter` (BSC chain) maps a different set of tick spacings to fees:

```solidity
tickSpacingToFee[1] = 100;    // 0.01%
tickSpacingToFee[10] = 500;   // 0.05%
tickSpacingToFee[50] = 2500;  // 0.25%
tickSpacingToFee[200] = 10000; // 1%
```

Tick spacings 100 and 2000 pass the Launch validation but have no fee mapping in the adapter (fee defaults to 0), causing `PancakeV3Adapter.launch()` to revert with `InvalidFee()`. Conversely, tick spacing 10 (PancakeSwap's 0.05% tier) is valid in the adapter but is blocked by Launch.

This means BSC launches using PancakeV3Adapter can only use tick spacings of 1, 50, and 200.

### Recommendations

Update the tick spacing validation in `Launch._onLaunchSuccess()` to be chain-aware or delegate the validation to the adapter.

## [L-02] TokenClaimed hardcodes 20/80 instead of the actual configured split

`Launch.claimTokens()` computes the real immediate and vested amounts from `percentageOfTokensToClaim`, but the emitted `TokenClaimed` event ignores that runtime value and always logs a fixed `20/80` split.

In `claimTokens()`, the actual transfers use:

- immediate amount: `_claimAmount * percentToClaim / 100`
- vested amount: `_claimAmount * (100 - percentToClaim) / 100`

But the event emits:

- immediate amount: `_claimAmount * 20 / 100`
- vested amount: `_claimAmount * 80 / 100`

This means any launch configured with a split other than 20/80 will produce incorrect event data even though token movement is correct.

### recommendation

Emit the actual computed values

- `immediate claimed amount = (_claimAmount * percentToClaim) / 100`
- `vested amount = vestAmt`
